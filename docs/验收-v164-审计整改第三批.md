## 三、已知边界与遗留

1. **并发多进程的清理竞态**：`_prune_sessions` 只知道**本进程**的 `protect` 目录。若两个
   XinRefinement 实例（或多用户共享 `%TEMP%`）同时打开不同工程，A 的回收可能删掉 B 正在使用的
   目录（B 已加载的数组在内存里，界面不会崩，但 B 之后若再次从临时目录路径读文件会失败）。
   最终修法应是会话目录加**进程级锁/活跃标记**（如 `<dir>/.lock` + 存活检查），属设计类改动，
   未纳入本批次（本批次目标是小修，且单实例桌面软件的默认使用形态下触发概率低）。
2. **工程重存不保留 `warnings`（也不保留 `result_full`）**：`apply_project` 只回填界面，
   按设计**不伪造** `self._result`（`SolveResult` 需要完整数据），所以「打开工程 → 直接另存」
   会丢掉内嵌结果与本次的 warnings 列表。要保留必须重跑精修。这是 R-2a 的既有设计取舍，
   本批次未改，**已写进 `_restore_result_panel` 的 docstring**。
3. **`id()` 缓存键的 GC 复用兜底**：`_esd_for` 的键含 `id(res)`，对象被回收后 `id` 可能被
   新对象复用。兜底是并放 `rwp/iters` + 相名与 cell 元组 + `id(self._phases)`，并
   `new_project()` 直接清空缓存。理论上仍存在「同一 `id` + 完全相同 rwp/iters + 完全相同的相集合
   但实为不同对象」的极端撞键窗口，此时会复用一份数值上等价的旧 e.s.d.（rwp/iters/相全同意味着
   拟合结果同值，风险可忽略）。彻底方案是让 `SolveResult` 自带单调序号，属契约改动，未做。
4. **会话目录命名 `{stem}_{int(mtime)}` 的两种撞名**（QA 独立验收也单列了这一条，编号 QA-03）：
   - *同一工程重复打开*：mtime 不变 → 同一目录 → 复用（**无害**，`_load_zip` 每次都会覆盖重写
     `pattern.xy` 与 CIF，不会读到陈旧数据）。跨秒重存 → 新开一个目录并多解压一次，旧目录留给回收。
   - *不同目录下的同名工程 + mtime 落在同一秒*：会**共用同一会话目录**（实测两个 `demo_*.xinr`
     命中同一目录）。单实例顺序打开时仍因「每次覆盖写」而正确，但两个窗口/两个进程同时使用时
     会互相覆盖对方的临时副本。彻底修法：目录名加 abspath 短哈希
     （`{stem}_{mtime}_{hash(abspath)[:8]}`），属命名契约改动，建议与 §三.1 的跨进程锁同批做。
   - mtime 在某些文件系统上粒度可达 2 s，因此「2 秒内重存」表现为复用、「2 秒以上」表现为重解压
     一次——两者都只是多/少一次解压，**不会读到陈旧数据**，属预期。
5. **manifest 声明了 `result_full` 但 zip 内缺该成员 → 仍静默 `None`、`warnings == []`**（QA-04）：
   `_load_zip` 只在「成员存在且解码失败」时告警，成员缺失走的是 `if rm and rm in zf.namelist()`
   的假分支。要一并提示需在同处补「声明了却找不到」的分支，属提示增强，本批次未做。
6. **合法 JSON 但非对象（如 `[1,2,3]`）会让 `apply_project` 抛 `AttributeError`**（QA-05）：
   `load_project` 照常返回（`result_full = [1,2,3]`，`warnings == []`），但 `_restore_result_panel`
   首行 `full.get(...)` 直接炸。**HEAD 同源，非本批次回归**；修法是 `if not isinstance(full, dict):
   full = {}` + 一条告警。已登记，未纳入本批次（本批次范围冻结在 5 张卡）。
7. **`_esd_for` 缓存键假设 `phase.cell` 恒为 tuple**（QA-06）：实测 `parse_cif` 的 `cell`
   确为 6 元 tuple，`tuple(getattr(p, "cell", ()) or ())` 成立；若将来把 `cell` 改成 ndarray，
   `or ()` 会因数组布尔歧义抛错——届时应改 `tuple(np.ravel(cell))`。属未来防护，当前无缺陷。
